# 렌더 배칭·메시 캐시 개선 리포트

작성일: 2026-09-22. 기준 커밋: `bc24ab2`. 변경 코드의 빌드/실행/실측은 수행하지 않았다.

## 1. 관측과 원인

사용자 제공 6개 구간은 FPS 52.7~54.2, 구간 평균 Draw Call 679.3~720.7, 최대 749이다. 구간 평균의 단순 산술 평균은 약 702.62회다. 원본은 `baseline_2026-09-22.txt`에 보관했다. 하드웨어·장면·옵션이 없으므로 이후 측정과 완전히 같은 조건이라고 가정하지 않는다.

코드에서 확인한 사항:

- 기존 `InitializeMeshes()`는 삼각형(3정점), 사각형(6정점), 원(48정점)을 렌더러 초기화 시 한 번 생성하고 GPU에 업로드한다. 기본 메시를 매 프레임 새로 생성하지는 않는다.
- 매 프레임 Actor가 `Triangle/Quad/Ellipse/Line/Text`를 호출하면서 화면 위치·색상 등의 **인스턴스 데이터**를 다시 작성하고 업로드한다. 기존 GPU 메시 재사용과 별개인 비용이다.
- `QueueMesh()`는 **서로 이웃한 같은 종류 메시**만 하나의 `DrawRun`으로 합친다. `원 → 삼각형 → 원 → 사각형` 형태의 캐릭터가 반복되면 캐릭터마다 여러 호출이 생긴다.
- 한글은 최초 사용 시 GDI로 래스터화하여 메모리에 캐시한다. 이후에도 글자 하나가 여러 coverage run 사각형 인스턴스로 제출된다. 메시 생성 없이도 UI 인스턴스와 업로드량은 클 수 있다.
- 현재 `glutTimerFunc(16, Tick, 0)`를 Tick 끝에서 다시 등록한다. 타이머 대기와 갱신 시간이 FPS에 영향을 주므로 53 FPS만으로 GPU 병목이라고 판단할 수 없다. 이번 변경에서 게임 타이밍 정책은 바꾸지 않았다.

## 2. 적용한 Draw Call 감소 방법

### 순서를 유지하는 혼합 메시 인스턴싱

세 메시를 하나의 GPU texture buffer atlas에 저장한다. 각 메시가 48개의 정점 슬롯을 사용하며 사각형·삼각형의 남는 슬롯은 `(0,0)`으로 채운다. 정점 셰이더는 인스턴스의 `mesh` ID와 `gl_VertexID`로 atlas를 조회한다. 현재 메시의 정점 수를 넘는 부분은 같은 위치의 세 정점이 되어 면적이 없는 삼각형으로 처리된다.

이제 한 `glDrawArraysInstanced()`가 서로 다른 도형을 포함할 수 있다. 인스턴스 배열 순서는 기존 제출 순서 그대로다. 도형 종류별 정렬을 하지 않아 반투명 그림자, 안개, 캐릭터 겹침, 한글 coverage의 순서를 유지한다.

이 방식은 현재 공통 셰이더·색상 재질·블렌딩 상태를 공유하는 3종 메시를 대상으로 한다. 향후 텍스처, scissor, 다른 재질/셰이더를 추가하면 해당 상태 변화에서 배치를 끊어야 한다. 임의의 복잡한 3D 메시까지 자동으로 같은 배치에 들어가는 구조는 아니다.

### 긴 동일 메시 구간 보호

혼합 배치에 원 하나가 있으면 그 배치의 모든 인스턴스가 최대 48정점을 처리한다. 글자 사각형 수천 개를 여기에 섞으면 드로우 콜은 줄어도 정점 비용이 커질 수 있다.

- 동일 메시가 **256개 이상** 이어지는 구간은 별도 인스턴싱한다.
- 나머지 짧은 구간끼리는 순서대로 합친다.
- 한 큐는 최대 **16,384 인스턴스**이며 넘으면 안전하게 Flush한다.
- 월드 → 후처리 → UI 경계는 항상 유지한다.
- 큐의 기존 capacity를 재사용한다. GPU 동적 버퍼 용량 증가는 별도로 집계한다.

페이지당 긴 구간이 L개일 때 geometry 호출 상한은 대략 `2L+1`이며, 비어 있는 짧은 구간은 제출하지 않는다. L=0이면 페이지당 geometry 1회다. 긴 구간마다 최대 한 호출이었던 기존 방식보다 배치 호출 수가 늘지 않도록 인접 run만 합친다. 큐 제한 때문에 페이지 경계가 생기는 점은 비교 시 고려한다.

### 후처리 호출은 별도

현재 설정 기준 후처리 호출 수는 다음과 같다.

| 옵션 | 후처리 호출 수 |
| --- | ---: |
| HDR 꺼짐/사용 불가 | 0 |
| HDR만 | 1 (최종 합성) |
| HDR + Bloom | 10 (추출 1 + 블러 8 + 합성 1) |
| HDR + 가장자리 블러 | 6 (블러 준비 1 + 블러 4 + 합성 1) |
| HDR + Bloom + 가장자리 블러 | 15 |

각 블러 패스는 이전 패스 결과를 읽으므로 geometry 배치와 합칠 수 없다. 비넷은 합성 셰이더에서 처리한다. 이번 변경은 후처리 품질/횟수를 유지한다. 실제 개선 후 호출 수/FPS는 **미측정**이다.

### F10 비교

- 기본 ON: 혼합 메시 배칭 + 긴 동일 메시 구간 분리.
- F10 OFF: 같은 캐시/셰이더/장면 데이터로 기존처럼 메시 종류가 바뀔 때마다 제출.
- OFF는 옛 실행 파일 전체를 복원하는 모드가 아니다. 배칭 정책만 비교한다.
- CSV의 `legacy_geometry_runs`는 같은 프레임을 기존 인접 메시 방식으로 제출했을 때의 geometry 호출 수다. 새 큐 페이지 경계도 포함된다.

## 3. 디스크 메시 캐시

실행 파일 옆 `Cache/primitives_v1.meshcache`를 사용한다.

1. 시작 시 캐시를 읽고 magic, 버전, 정점 슬롯 수, 메시 수, 메시별 정점 수, 정확한 파일 길이, checksum, 좌표 범위, 패딩을 검사한다.
2. 정상 파일은 재사용한다: `status=disk_hit loaded=3 generated=0`.
3. 파일이 없거나 검증 실패이면 세 기본 메시를 생성하여 임시 파일에 저장한 뒤 원자적으로 교체한다: `generated_and_saved`.
4. 읽기/쓰기 권한이 없으면 메모리 메시로 계속 실행한다: `memory_fallback`.
5. GPU atlas는 실행마다 한 번 업로드한다. 프레임마다 캐시 파일을 읽거나 쓰지 않는다.

현재 Windows float32/uint32 형식으로 헤더 32바이트 + 정점 1,152바이트, 총 1,184바이트다. checksum은 손상 탐지용이며 보안 서명이 아니다. 생성 규칙·원 분할 수·파일 레이아웃 변경 시 버전과 파일명, 셰이더의 48-slot 계약도 함께 변경해야 한다.

파일 캐시는 **시작 간 기본 메시 재사용**을 제공한다. 이것만으로 프레임 FPS가 크게 개선된다고 주장하지 않는다. Actor별 동적 좌표·색상, 카메라 변환, 글리프 coverage는 이 파일에 저장하지 않는다. 무한 월드 위치별 캐시 파일도 만들지 않는다.

## 4. 지속적인 분석 로그

실행 파일 옆 `Logs/renderer_<UTC 시각>_<PID>.csv`와 같은 이름의 `.log`가 생성된다. 실행마다 새 세션 파일을 만들며 기존 로그를 덮어쓰지 않는다. CSV에는 프레임별 기록을 모아 약 1초마다 기록한다. 장면/설정이 바뀌면 이전 구간을 먼저 기록하고 segment를 바꾼다. 종료 시 남은 기록을 쓴다. 비정상 종료 시 마지막 버퍼 구간이 유실될 수 있다.

| 데이터 | 의미 |
| --- | --- |
| `.log` 시작 정보 | GPU vendor/renderer, OpenGL/GLSL, 캐시 상태, 생성/로드 개수, 알고리즘 버전 |
| `frame`, `seconds`, `segment`, `scene` | 프레임 ID, 세션 경과 시간, 설정 구간, world/level_one |
| 화면 크기·HDR·Bloom·edge blur·vignette·exposure·batching | 비교 조건 |
| `draws`, `world_draws`, `ui_draws`, `post_draws` | 실제 glDraw 호출 수. 인스턴스 수와 무관하게 호출당 1회 |
| `world_instances`, `ui_instances` | 프레임에 제출한 geometry 인스턴스 수 |
| `useful_vertices`, `submitted_vertices` | 원래 필요한 geometry 정점 수와 패딩 포함 제출 수. 실제 하드웨어 shader invocation 카운터는 아님 |
| `upload_bytes`, `upload_cpu_ms` | 동적 인스턴스 업로드량과 해당 API 구간 CPU 경과 시간 |
| `submit_cpu_ms` | geometry glDraw 호출 및 계측 구간 CPU 경과 시간. GPU 실행 시간이 아님 |
| `buffer_growths`, `queue_growths` | GPU 인스턴스 버퍼와 CPU 큐 용량 증가 횟수. 메시 생성 횟수와 별개 |
| `flushes`, `legacy_geometry_runs` | 비어 있지 않은 Flush 수와 기존 방식의 geometry run 수 |
| `glyph_hits`, `glyph_misses` | 해당 프레임의 글리프 조회 재사용/최초 생성 수 |
| `mesh_generations` | 프레임 중 기본 메시 생성 수. 현재 구조의 정상 값은 0, 시작 시 생성은 `.log`에 별도 기록 |
| `update_cpu_ms`, `update_ticks` | 이번 출력 사이에 실행한 Update 누적 시간/횟수 |
| `render_cpu_ms`, `swap_cpu_ms` | Draw/GL 제출 경과 시간, SwapBuffers 대기 포함 경과 시간 |
| `gpu_ms`, `gpu_frame` | 가장 최근 회수한 GPU elapsed query 값과 **원래 측정 프레임** |
| `gpu_query_skipped` | 네 query가 모두 대기 중이어서 해당 프레임 측정을 생략했는지 |
| `frame_ms`, 콘솔 FPS/p95 | 실제 프레임 간격, 시간 합계 기반 FPS, 구간 프레임 시간 95백분위 |
| `last_log_flush_ms` | 직전 로그 기록 작업 비용. 현재 CSV 배치를 쓰는 데 드는 비용은 다음 기록에서 관측 |

GPU 쿼리는 사용 가능 여부를 확인한 뒤에만 읽으며 `glFinish`를 호출하지 않는다. GPU 결과는 지연되어 같은 값이 여러 행에 반복될 수 있다. 반드시 `gpu_frame`으로 연결하고 중복을 제거해야 한다. GPU elapsed는 명령 구간의 시간으로 CPU 공급 지연의 영향도 받을 수 있으며 GPU 점유율 측정은 아니다. 마지막 몇 GPU 결과는 종료 시 미회수일 수 있다.

콘솔은 1초 단위 요약이며 프레임별 로그는 CSV가 원본이다. 로그 I/O 자체의 영향도 있고 VSync 설정은 조회하지 않는다. `glutTimerFunc` 대기·창 비활성화·디버거 정지는 frame_ms에 포함된다. 무제한 장시간 기록 시 파일 크기는 증가하므로 필요 세션을 보관하고 나머지는 사용자가 관리한다. 자동 삭제는 하지 않는다.

## 5. 비교 절차와 분석 도구

빌드와 실행은 사용자가 수행한다. 캐시/로그 디렉터리는 실제 실행 시 생성된다.

1. 같은 Release 구성, 같은 창 크기·장면·저장 데이터로 실행한다.
2. 시작 캐시 로그를 확인하고 5초 이상 워밍업한다.
3. 같은 위치/시점에서 batching ON으로 30초 이상 기록한다.
4. F10으로 OFF 전환 후 다시 5초 워밍업, 30초 기록한다. 가능하면 ON/OFF/ON 반복으로 시간 경과 영향을 확인한다.
5. 마을·레벨 1을 각각 측정한다. 적 스폰/카메라 이동이 달라지면 완전한 A/B가 아니므로 인스턴스·legacy run 수가 비슷한 구간끼리 비교한다.
6. F6/F7/F9 조건은 별도 구간으로 기록한다. 저장/전승/로딩/최초 글리프 생성은 따로 해석한다.
7. Python 3 환경에서 다음 분석 도구를 실행한다.

```text
python Tools/analyze_render_log.py "실행폴더/Logs/renderer_....csv"
python Tools/analyze_render_log.py "실행폴더/Logs/renderer_....csv" --warmup-seconds 5 --output comparison.md
```

기본 출력은 CSV 옆 `<세션>_analysis.md`다. 설정 segment별 FPS, p50/p95/p99, 호출 수, geometry 호출 감소율, 정점 패딩 비율, 업로드, CPU/GPU 시간, 카운터 이상을 정리한다. GPU 샘플은 원래 프레임과 연결해 중복 제거한다. CSV 열이 손상되면 오류를 내며 원본을 덮어쓰지 않는다.

판단 기준:

- Draw 수가 감소하고 render/submit CPU 시간도 감소하면 드라이버 제출 비용 절감 근거가 된다.
- Draw 수는 감소했지만 GPU 시간이 늘고 정점 패딩 비율이 높다면 배치 임계값을 조정한다.
- UI 인스턴스/업로드가 지배하면 다음 작업은 글리프 텍스처 atlas 또는 문자열 레이아웃 캐시다.
- update CPU가 지배하면 SceneGraph 타입 조회/순회/정렬과 충돌·경로 탐색을 별도 프로파일링한다.
- upload CPU가 지배하면 버퍼 orphaning/링 버퍼/비동기 갱신을 비교한다. 이번 변경은 기존 SubData 방식을 유지한다.
- GPU 시간이 지배하고 후처리 비중이 의심되면 후처리별 timer query와 해상도/블러 패스 비교를 추가한다.

## 6. 향후 변경 기록 규칙과 검증 범위

`Docs/Performance/CHANGELOG.md`에 날짜, 기준 커밋, 가설, 변경, 데이터 경로, 검증 상태, 결론을 누적한다. 실측하지 않은 값은 예상으로 명시한다. 변경한 코드와 함께 알고리즘/캐시/CSV 스키마 버전을 남긴다. 자동 로그는 .gitignore 대상이므로 공유할 비교 자료만 문서 폴더에 복사한다.

이번 작업의 정적 검토 항목: VS 소스 등록, C++/GLSL 인스턴스 속성 및 슬롯 계약, 모든 glDraw 계측 지점, 큐 순서와 패딩, 캐시 길이/검증, GPU 쿼리 회수 조건, CSV 열 수와 분석기 구문, 기존 게임/저장 데이터 미변경.

미수행: C++ 빌드, GLSL 컴파일, 게임 실행, 시각 비교, GPU 드라이버별 측정, 캐시 손상/권한 오류 실환경 재현. 사용자는 특히 F10 ON/OFF에서 반투명 가림·원·한글·Bloom 출력 동일성을 확인해야 한다. 성능 향상 수치를 아직 확정하지 않는다.

기술 참고: [Khronos Vertex Rendering](https://wikis.khronos.org/opengl/Instancing), [OpenGL 3.3 Core Specification](https://registry.khronos.org/OpenGL/specs/gl/glspec33.core.pdf). 인스턴싱, buffer texture, query는 OpenGL 3.3 경로를 사용하며 최신 버전의 multi-draw indirect 기능은 요구하지 않는다.
